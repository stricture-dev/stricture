Stricture provides battle-tested presets for popular architectural patterns. Each preset comes with pre-configured boundaries and rules that enforce best practices out of the box.

## What Are Presets?

Presets are pre-packaged architectural configurations that include:

- **Boundary definitions** - File patterns that define architectural layers
- **Enforcement rules** - Dependency constraints between layers
- **Best practices** - Battle-tested patterns used in production

Instead of manually defining boundaries and rules, you can use a preset and get started immediately:

```json
{
  "preset": "@stricture/hexagonal"
}
```

## Understanding Package Dependencies

Stricture has a clear package architecture:


**What you install:**
- **ESLint Plugin** - Integrates with ESLint to enforce rules
- **Preset Package** - Contains boundaries and rules for your architecture

**What gets installed automatically:**
- **Core Package** - Shared validation logic (transitive dependency)

### Installation Pattern

Install the plugin once - all presets are bundled:
```bash
npm install -D @stricture/eslint-plugin
```

Then use any preset in your config:
```js
import stricture from '@stricture/eslint-plugin'

// Hexagonal architecture
export default [stricture.configs.hexagonal()]

// Next.js patterns
export default [stricture.configs.nextjs()]

// Custom config
export default [stricture.configs.recommended()]
```

:::tip[Everything Bundled]
All official architecture presets are bundled with the plugin. `@stricture/core` is automatically included as a dependency.
:::

## Why Use Presets?

### Zero Configuration

Presets work out-of-the-box with common project structures. No need to define boundaries or rules manually.

### Battle-Tested Patterns

Each preset embodies proven architectural patterns used successfully in production applications.

### Consistency

Using presets ensures consistent architecture across your organization's projects.

### Learning Tool

Presets serve as reference implementations, helping teams learn architectural patterns through enforcement.

## How to Choose?

### Choose Hexagonal if you have:
- Complex business rules
- Domain-Driven Design approach
- Need for adapter swappability
- Multiple entry points (CLI, HTTP, GraphQL)

### Choose Layered if you have:
- Traditional application structure
- Team familiar with N-tier patterns
- Straightforward business logic
- Need for simplicity

### Choose Clean if you have:
- Enterprise application requirements
- Strict dependency control needs
- Framework independence as priority
- Long-term maintainability focus

### Choose Modular if you have:
- Large application
- Multiple teams working on features
- Need for module isolation
- Feature-based organization

### Choose Next.js if you have:
- Next.js App Router application
- Server/Client Component separation needs
- Server Actions usage
- Next.js-specific patterns

### Choose NestJS if you have:
- NestJS application
- API backend structure
- Dependency injection patterns
- TypeScript decorators

```bash
npm install --save-dev @stricture/eslint-plugin
# or
pnpm add -D @stricture/eslint-plugin
# or
yarn add -D @stricture/eslint-plugin
```

## Usage

Create `.stricture/config.json` and reference the preset:

```json
{
  "preset": "@stricture/hexagonal"
}
```

That's it! The preset defines all boundaries and rules for you.

## Customization

You can extend or override preset configurations:

```json
{
  "preset": "@stricture/hexagonal",
  "boundaries": [
    {
      "name": "shared",
      "pattern": "src/shared/**",
      "mode": "file",
      "tags": ["shared"]
    }
  ],
  "rules": [
    {
      "id": "all-to-shared",
      "from": { "tag": "*" },
      "to": { "tag": "shared" },
      "allowed": true
    }
  ]
}
```

:::tip[Start Simple]
Start with a preset as-is. Only customize when you have specific needs that differ from the preset's assumptions.
:::

## Multiple Presets

You cannot use multiple presets simultaneously. Each preset defines a complete architectural pattern.

If you need multiple patterns in a monorepo, use separate `.stricture/config.json` files in each package.

## Creating Custom Presets

You can create organization-specific presets by following the same structure:

```typescript
import type { ArchPreset } from '@stricture/core'

export const myPreset: ArchPreset = {
  boundaries: [
    // Your boundary definitions
  ],
  rules: [
    // Your rules
  ]
}
```

See the [API Reference](/api/types#archpreset) for details.
